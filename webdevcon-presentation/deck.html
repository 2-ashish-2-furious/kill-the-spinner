The whole trick, in three steps

1
Replicate
The server mirrors the relevant slice of data into a live local store in the browser.
2
Read locally
The UI reads from that local copy. No fetch, no spinner.
3
Sync & merge
Writes apply optimistically and sync up; concurrent edits reconcile.
Same three steps, whatever the backend.

The hard part is off the shelf

Until recently you built it
Sync was bespoke infrastructure: change capture, reconciliation, live queries, all yours.
Figma and Linear each spent years and millions building theirs.
So local-first meant being a company that could afford that.
Now you install it
The sync engine is a dependency, open source and Postgres-native.
Logical replication feeds it; the client store is ~20 KB.
So local-first is a library choice, not a roadmap.
they each built their own
Figma Linear
now you install one
ElectricSQLTanStack DBZeroPowerSync + 6 more
The idea isn't new. What changed is that you no longer have to build it.

Partial replication & fan-out

You don't ship the database. You declare a slice, and only that subset syncs. Declared once on the server, so every client entitled to it rides the same cached stream.

Local·FirstWebDevCon '26

You choose how much to sync

1
Eager the default
best for under ~10k mostly-static rows: reference tables, settings
one wait at the start, then never again
2
On-demand
best for large datasets, search, catalogs. Your query is the API call
a brand-new query waits, but only once
3
Progressive
best for collaborative apps and big shared data
instant now, complete a moment later
The "but it loads the whole database!" critique is really just the eager default.

Why long-polling, not WebSockets

WebSockets what you'd own
An opaque stream: nothing in the middle can cache it.
Stateful: every client pinned to one process.
HTTP long-poll what you inherit
One URL per slice: your CDN and 304s just work.
Stateless: any server answers any poll.
The boring protocol is the feature.
The trade is a little latency against a socket push. That costs nothing, because the UI already painted from the local store.

Where it earns its complexity: conflicts

Server-authoritative
+ rollback
The default. Your optimistic change applies instantly; if the server rejects it, it rolls back. Effectively last-write-wins.
Merge per field
Two people edit different columns of the same row and both survive. No CRDT, just stop overwriting whole rows.
CRDTs
Two cursors inside one value: documents, canvases, presence. Powerful, and genuinely deep.
start with the Ink & Switch paper
Start at the left. Move right only when a user complains.

Local·FirstWebDevCon '26

When to just fetch

1
Read once, then closed
Reports, exports, a dashboard you open and leave. No second read to make instant.
2
Plain CRUD
A form, a save, a redirect. No interactivity for a local replica to speed up.
3
Must not touch the device
Regulated or sensitive enough you don't want it cached in a browser at all.
4
Rules a filter can't express
Per-access audit, purpose-based access, field redaction. Not a WHERE clause.
Rule of thumb: touched more than once → sync it. Seen once and gone → fetch it.
Local-first is a tool, not a religion.
